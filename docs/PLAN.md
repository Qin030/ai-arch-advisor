# AI 建築前期決策助理｜10 天最小 MVP 分工與流程規劃

**團隊：鳳梨田NPC｜人力：2 人 × 4 小時/日 × 10 天 = 80 人時**
**工具：M1（Claude Code、Codex、Gemini）／M2（Codex、Gemini）**

---

## 一、角色決策（結論先講）

| 項目 | 決定 | 理由 |
|---|---|---|
| **Agent 組長／整合負責人** | **M1** | Claude Code 是唯一能持有整個 repo 上下文、跑測試、操作 git 的工具，整合角色必須落在有這個工具的人身上。 |
| M1 主力 agent | **Claude Code** | 負責核心程式：API、規則層、檢索層、整合與 merge 前的最終驗證。 |
| M1 的 reviewer | **Gemini（規格審查）＋ M2 人類（PR approve）** | 不同模型家族做交叉審查，避免同源盲點。 |
| M2 主力 agent | **Codex** | 負責資料層、UI、測試案例、匯出功能等邊界清楚的模組。 |
| M2 的 reviewer | **M1 的 Claude Code（能實跑驗證）＋ M1 人類（PR approve）** | Claude Code 可實際執行測試，是最強的 PR 把關者。 |
| **企畫書文字與口徑** | **M1（原始作者，唯一寫作者）** | 論述線是連動的，只有作者拿得住。見下方說明。 |
| 企畫書機械回填 | **M2** | 圖 2／圖 3 插入、表格格式、參考資料、錯字、打包。 |
| **企畫書宣稱一致性審查** | **M2（含實質否決權）** | **作者不能審自己的宣稱。** 見下方說明。 |
| Gemini 的定位 | **雙方共用的「長文脈審查員 + 文件手」** | 讀法規長文做切片、審 PR diff 的規格一致性、審企畫書中文、產測試腳本。 |

### 企畫書歸屬：M1 執筆、M2 審查

企畫書原始作者是 M1，因此由 M1 繼續執筆。三個理由：

1. **論述線是連動的。** MVP 縮到只有臺南市之後，「第一階段涵蓋六都及鄰近縣市」這句話牽動至少三處——五大知識庫段、SAM 市場規模推估、護城河第四點。改了一處漏掉另兩處，全文就自相矛盾。只有作者知道這些線跑到哪裡。
2. **這份文件的措辭是刻意的。** 「不代為判定」「轉列待確認」「沒把握就轉為待確認」這類定位語，換人重寫很容易寫鬆；鬆掉了，整個差異化定位就垮了。
3. **交給 M2 寫再由 M1 改，等於做兩次。** 那不是分擔，是加倍。

**代價：** M1 現在同時是組長＋主力開發＋文件作者，4 小時/日扛不住。因此做兩件事平衡（已反映在第六節）：

- **開發後移：** D8 起 M1 交出主要實作，Claude Code 轉為修 bug 與整合驗證，M2 的 Codex 接手剩餘開發。
- **寫作分散：** 企畫書不堆在 D10。M1 在 D1／D6／D8／D9 各花 1 小時隨數據到位增量更新，D10 只剩 2 小時定稿。

### 為什麼審查權必須移到 M2

原版把「企畫書每句宣稱是否做得到」放在 M1。**在 M1 是作者的前提下，那是自我審查，違反本規劃第一條鐵律。**

移交 M2 的理由：M2 對文字沒有作者的護短本能；M2 親手建知識庫、跑題組、做使用者測試，最清楚實際做到什麼；M2 是唯一能在 D10 說出「這句話我們的程式做不到，拿掉」而不會心痛的人。

**M2 的否決權是實質的。** M1 可以不同意，但要拿程式碼或實測數據來反駁，不能用「本來就是這樣寫的」。這條規則現在就要講清楚，不要留到 D10 兩個人在文件上吵。

### 兩條不可妥協的鐵律

1. **產出者 ≠ 審查者**：寫程式的 agent 不能審自己的 PR；寫實作的 agent 不能寫該功能的測試。
2. **Agent 不得 merge**：所有 merge 由人類按下，且必須是「另一個人」。

### 交叉分工的關鍵設計：測試與實作分離

> **M2 的 Codex 依規格先寫測試 → M1 的 Claude Code 再寫實作讓測試變綠。**

這是本規劃最重要的一條。同一個 agent 寫實作又寫測試，會寫出「剛好符合自己 bug」的測試。拆給不同人、不同模型，測試才是真的契約。

## 三、檔案所有權切分（防止 agent 把 diff 搞爆）

Agent 一次改 20 個檔案是常態，兩人平行開發時衝突會失控。因此**先切目錄所有權**：

| 目錄 | Owner | 內容 |
|---|---|---|
| `app/api/` `app/core/` `app/rules/` `app/retrieval/` | **M1** | FastAPI、規則引擎、檢索器、摘要生成 |
| `data/kb/` `ui/` `tests/spec/` `docs/` | **M2** | 知識庫切片、Streamlit UI、規格測試、技術文件 |
| `docs/proposal/` | **M1（作者）** | 企畫書 .docx 主檔——唯一由 M1 獨佔的文件目錄 |
| `schema/` `docs/CONTRACT.md` | **共同（需雙方 approve）** | 資料契約——動這裡要兩人都點頭 |

`CODEOWNERS` 直接把上表寫死，GitHub 會自動指派 reviewer。

## 四、GitHub 協作規則

### 分支與 PR

```
main（受保護，禁止直推）
 ├── feat/rules-refusal-engine      ← 功能
 ├── fix/ui-empty-state             ← 修錯
 ├── data/kb-tainan-regulation      ← 知識庫
 └── docs/proposal-metrics          ← 企畫書
```

**規則：**

1. `main` 開啟 branch protection：**需 1 個 approval ＋ CI 綠燈**才能合併。
2. **單一 PR diff 上限 400 行。** 超過就退回拆小——這是控制 agent 的最有效手段。
3. PR 一律 **cross-review**：M1 開的 PR 由 M2 approve，反之亦然。
4. Agent 可以開 PR、可以留 review comment，**但按 merge 的一定是人類**。
5. 每天收工前 `main` 必須能跑 `make demo`。**綠燈才能下班。**
6. Commit 用 Conventional Commits：`feat:` `fix:` `test:` `docs:` `data:`。

### CI（GitHub Actions，免費額度足夠）

```yaml
on: [pull_request]
jobs:
  ci:
    - ruff check .          # lint
    - pytest -q             # 全部測試
    - python scripts/validate_kb.py   # 知識庫 metadata 必填檢查
```

第三項很關鍵：**任何一筆知識庫切片少了來源、版本或適用地區，CI 直接紅燈。** 這讓「可查核性」變成機器強制，而不是靠人記得。

### PR 模板（`.github/pull_request_template.md`）

```markdown
## 對應 Issue
Closes #

## 變更摘要

## 主要由哪個 agent 產出
- [ ] Claude Code  - [ ] Codex  - [ ] Gemini  - [ ] 純人工

## 我人工確認過的部分
（agent 產出不等於已驗證，請寫你實際跑過/讀過什麼）

## 測試
- [ ] 新增/修改測試，且在本機綠燈
- [ ] 對「拒答」行為的影響：無／有（說明）

## 風險與已知限制
```

「主要由哪個 agent 產出」這欄不是形式——reviewer 看到是 agent 大量產出時，會用不同的力道去審。

### 企畫書的版本控管（.docx 特別處理）

Word 檔在 git 裡無法合併，所以：

- **只有 M1（作者）能開啟編輯**，檔名帶日期：`提案書_v3_0905.docx`
- 每次改動走 `docs/proposal-*` 分支，PR 內同時更新 `docs/CHANGELOG.md`（純文字，可 review）
- **M2 審 CHANGELOG，逐條問「這句話程式做得到嗎」**；審不過就 request changes
- 圖檔與表格素材由 M2 產出後放 `docs/assets/`，M1 負責插入
- 舊版保留在 `docs/archive/`，不覆蓋

## 五、十天流程總覽

```
D1 ──────► D2 ──────► D3-D4-D5 ──────► D6-D7 ──────► D8 ──────► D9-D10
契約凍結    走通骨架     核心功能         輸出與 UI     功能凍結    驗證與定稿
           (假資料)                                    (只修 bug)
   ▲          ▲                ▲                          ▲            ▲
   M1         M1               M1                         M1           M2
 定契約    整合驗收          整合驗收                    喊凍結      審宣稱一致性
 ＋口徑盤點                                            ＋交出實作     （作者迴避）
```

**M1 的重心會在 D8 轉向：** D1–D7 是開發與整合，D8–D10 是企畫書與整合驗證，實作交給 M2 的 Codex。

### 五個里程碑

| 里程碑 | 日 | 判定標準（做不到就啟動停損） |
|---|---|---|
| **M0 契約凍結** | D1 收工 | `schema/` 與 `docs/CONTRACT.md` 合併進 main，雙方 approve |
| **M1 走通骨架** | D2 收工 | `make demo` 用假資料跑完 輸入→追問→摘要 全流程 |
| **M2 真實端到端** | D5 收工 | 拿掉假資料，真的檢索、真的拒答，20 題題組能跑 |
| **M3 功能凍結** | D8 開工 | 之後只准 `fix:` 與 `docs:`，任何 `feat:` 一律拒收 |
| **M4 繳交包完成** | D10 收工 | 企畫書定稿＋Demo 影片＋repo tag `v0.1.0` |

## 七、每日 4 小時的時間配置模板

| 時段 | 內容 |
|---|---|
| 0:00–0:15 | 看 `main` 是否綠、看昨天未合併的 PR |
| 0:15–0:30 | 非同步同步（GitHub Issue 留言即可，不用開會） |
| 0:30–3:00 | **主力 agent 開發**——人類負責下規格、看輸出、擋掉亂改 |
| 3:00–3:45 | **審對方的 PR**（這 45 分鐘不可壓縮） |
| 3:45–4:00 | 更新 Issue 狀態、寫一行當日日誌 |

**M1 的變形版（因為兼任企畫書作者）：** D1、D6、D8、D9 這四天，把 `0:30–3:00` 的開發時段壓成 2 小時，挪 1 小時寫企畫書。D10 則整段用於定稿。

**兩人不需要同時上線。** 全程用 GitHub Issue 與 PR 非同步溝通，10 天內開會不超過 3 次（D1 契約、D5 整合、D8 凍結）。

|---|---|---|

## 八、風險與停損規則

| 風險 | 觸發條件 | 停損動作 |
|---|---|---|
| 檢索層做不完 | D5 收工未綠 | 砍掉向量檢索，改**純關鍵字 + metadata 過濾**。25 筆切片用關鍵字完全夠，Demo 看不出差別。 |
| UI 吃掉太多時間 | D7 未完稿 | 砍掉多方案比較的互動，改**靜態表格**（企畫書表 2 本來就標示為示例）。 |
| Agent 產出品質失控 | 單一 PR 修 3 次以上仍不對 | 換一個 agent 重做，不要在同一個對話裡硬凹。M1 可換 Claude Code ↔ Codex。 |
| 兩人進度差距過大 | 任一方落後 2 天以上 | M1 把該模組收回自己做，M2 改為只做知識庫與使用者測試。**保 Demo 不保分工**。 |
| **M1 超載**（組長＋開發＋作者） | D6 收工時企畫書一個字沒動 | 立刻執行 D8 的重心轉向，提前到 D7：M1 交出所有實作，Codex 全接。**企畫書優先於功能**——功能少一項還能 demo，企畫書沒改完就是交不出去。 |
| 企畫書與程式各說各話 | D10 稽核發現 3 條以上對不上 | 一律砍宣稱，不補功能。功能凍結後不准為了圓一句話而寫程式。 |
| 使用者找不到 | D8 仍未約到 3 人 | 降為 3 人，並補做「客觀情境題」（企畫書已規劃）作為替代證據。 |
| 法規切片有誤 | 抽查發現捏造條號 | **立刻停下所有開發**，全部 25 筆重查。這一項出錯，整個作品的立論就垮了。 |

**內建緩衝：** D7 下半天與 D8 是彈性區。若前期落後，直接吃掉這兩段，不要壓縮 D9 的使用者測試——**沒有實測數據的企畫書，比功能少一項嚴重得多**。
