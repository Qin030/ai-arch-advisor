# 拒答與結束前需求掃描

對應 `docs/SCOPE.md`〈做（十項）〉#6 拒答、#7 結束前需求掃描。服務範圍：
`POST /summary` 回應中的 `scan`、`confirmations`，以及拒答對三份文件內容的影響。

**這份規格描述行為，不描述實作。** 供 M2 依此撰寫規格測試；撰寫測試前不要
閱讀實作。

## 一、前提：拒答是回傳值，不是錯誤

`docs/CONTRACT.md`〈設計前提〉1 已定：資料不足時 HTTP 仍回 200，其餘欄位照常
產出。本規格不引入任何 4xx。

〈設計前提〉4 與已合併的 #30 進一步定：完整性條款（`required`／`minLength`／
`minItems`／`anyOf`）不在追問階段擋，缺漏一律留到這裡揭露。因此**本規格是缺漏
的唯一出口**。

## 二、輸入

結束前掃描的輸入是**伺服器累積的需求物件**，不是單一請求的欄位：

- 使用者在六組追問裡實際填入的值（含空白、部分填寫、整組跳過）
- 適用地區
- 檢索回來的切片及其版本日期

**不接受推定值作為輸入。** 使用者沒填的欄位就是沒填，不得以預設值、鄰近地區
規定或其他欄位反推補齊。

## 三、輸出

### 3.1 `scan` 的三種狀態

`docs/CONTRACT.md` 定義三個清單，對應企畫書的「已填、可推定但未確認、缺漏」：

| 清單 | 內容 |
|---|---|
| `filled` | 使用者實際填了值的欄位，以「群組.葉欄位」表示 |
| `assumed` | 見〈七〉待決 A——目前沒有任何來源定義什麼可以進這個清單 |
| `missing` | 應填而未填的欄位 |

同一個欄位只能出現在一個清單裡。

### 3.2 `confirmations`：待專業人員確認清單

每一筆是四個必填欄位加一個 `blocks`，缺一不可：

| 欄位 | 內容 |
|---|---|
| `missing_field` | 缺哪個欄位，以「群組.葉欄位」表示 |
| `confirm_with` | 找誰確認 |
| `impact` | 影響什麼 |
| `reason` | 為何無法判定 |
| `blocks` | 因此不生成的輸出欄位清單 |

**四個描述欄位缺任何一個，這一列就是殘缺的**——它直接組成使用者拿去問專業
人員的清單，少一項就少一個能問的東西。

### 3.3 對三份文件的影響

觸發拒答時，**只有 `blocks` 列出的輸出欄位不生成，其餘內容照常產出**。整份
摘要不得因為一條拒答而變空。

`blocks` 裡的欄位在摘要中的處理：不出現、不以「約」「可能」等措辭給近似值、
不留空字串佯裝已生成。

### 3.4 `confirmations` 的排列順序

`docs/SCOPE.md`〈做（十項）〉#7 要求缺漏「**依優先序**一次列出並說明影響」。
順序取 `schema/requirement.schema.json` 各群組的 `x-priority`：基地 1、家庭
成員 2、預算 3、光線 4、動線 5、數位設備 6。

不另外發明優先級，也不依「嚴重程度」重排——`x-priority` 已經是追問順序的
依據（見 `docs/specs/translation-tree.md`〈二〉），缺漏清單用同一個順序，
使用者看到的次序才與剛才作答的次序一致。

不由 `x-priority` 承載的情境（地區未收錄、成本資料過期）排在六組之後。

## 四、六個必測情境

觸發條件與確認對象的權威來源是 `app/rules/CLAUDE.md` 的情境表；四個描述欄位
的權威來源是 `schema/requirement.schema.json` 各群組的 `x-refusal`。兩者不一致
時見〈七〉待決 B。

### 情境 1：無地號或使用分區

- **觸發**：`site` 群組的地號與使用分區皆未填（行政區單獨存在不算填）
- **`confirm_with`**：建築師
- **`impact`**：可建樓地板面積與樓層數
- **`reason`**：未提供地號或使用分區，無法取得適用之建蔽率與容積率
- **`blocks`**：建蔽率、容積率、退縮規定三項輸出

### 情境 2：無家庭成員資料

- **觸發**：`household` 群組的居住人數未填
- **`confirm_with`**：見〈七〉待決 B
- **`impact`**：空間配置建議
- **`reason`**：未提供家庭成員資料，無法生成空間配置相關描述
- **`blocks`**：空間配置相關輸出

### 情境 3：地區未收錄

- **觸發**：適用地區不在允許清單內。允許清單只有臺南市
- **`confirm_with`**：建築師
- **`impact`**：全部法規判定
- **`reason`**：本系統現階段僅收錄臺南市資料，其他地區不作判定
- **`blocks`**：見〈七〉待決 C——`x-refusal` 對這一條給的是 `all_regulation`
  而非欄位清單

**這一條不得有任何 fallback。** 查無臺南以外的地區時，不得套用鄰近縣市規定、
不得以「一般而言」給通則、不得只加註警語就照常輸出法規判定。

### 情境 4：成本資料版本過期

**這一條不是四欄位拒答。** 過期是知識庫切片的屬性，不是使用者輸入的欄位。

- **觸發**：檢索回來的切片，其版本日期距今超過過期門檻。門檻為 365 天
- **行為**：該筆引用標記為過期，並在引用處附過期警示
- **不做的事**：不因為過期就把該筆切片整個丟棄，也不改用未過期但不適用的
  其他切片替代
- 見〈七〉待決 D——比較基準日與警示文案皆未定義

### 情境 5：智慧情境未填

- **觸發**：`smart` 群組的智慧情境未填，或填了但一項都沒選
- **`confirm_with`**：中華電信
- **`impact`**：全屋 Wi-Fi 涵蓋及是否需事後補線
- **`reason`**：未確認智慧情境需求，不生成弱電、網路孔位與設備電源描述；
  實際光纖引進點、AP 佈點與頻寬方案須由中華電信評估
- **`blocks`**：弱電、網路孔位、設備電源三項輸出

### 情境 6：色溫未填

- **觸發**：`lighting` 群組的色溫未填
- **`confirm_with`**：室內設計師或水電技師
- **`impact`**：照明氛圍與後續換裝彈性
- **`reason`**：未確認色溫偏好，不生成色溫描述；實際照度、燈具型號與迴路
  數量須由專業人員判定
- **`blocks`**：色溫描述

## 五、文案規則

拒答文案**不得軟化**。禁止「可能約為」「一般而言」「通常來說」「大約」這類
措辭出現在拒答路徑上。

正確的形狀是：**資訊不足，無法判定〈X〉，請補充〈Y〉。** 不是「建議您補充」，
也不是「若能提供將更精確」。

`reason` 說明的是「為何無法判定」，不是「這個欄位是什麼」。

## 六、邊界情況

1. **整組跳過與整組留白，結果相同。** 使用者對某一組按跳過、或送出空物件，
   在掃描階段是同一件事：該組的必填欄位進 `missing`，對應拒答觸發。追問階段
   已經允許兩者，掃描階段不得因為「跳過」而額外懲罰或額外寬待。

2. **部分填寫的群組。** 一組裡填了一部分（例如填了居住人數但沒填作息），
   已填的葉欄位進 `filled`，未填的必填葉欄位進 `missing`。**不因為同組有其他
   欄位已填，就推定未填欄位的值**，也不因為某個葉欄位未填就把整組視為未填。

3. **多條拒答同時觸發。** 每一條各自產生一列 `confirmations`，不合併、不因為
   數量多就摘要成一句。各自的 `blocks` 取聯集後不生成。

4. **地區未收錄且其他欄位也缺。** 情境 3 與情境 1／2／5／6 可同時成立，各自
   出一列。情境 3 不吸收其他條。

5. **值域外的值。** 填了型別正確但不在允許值域內的內容（例如色溫填了列舉以外
   的字串），見〈七〉待決 E。

6. **全部六組都跳過。** 掃描仍須產出完整的 `confirmations`，摘要仍須產出
   `blocks` 以外的內容，不得回空物件或錯誤。

7. **完全沒有可引用的切片。** 知識庫為空或檢索無結果時，依賴引用的輸出不生成，
   不得以模型記憶補寫。這一條與情境 4 不同：過期是有來源但太舊，無結果是沒有
   來源。

## 七、契約不足之處：需 M1／M2 決定，本規格不自行認定

以下五項在現有契約、schema 與規則層說明中找不到答案。**依 `/spec` 的規定，
列出而不自行填答。**

**A. `assumed` 清單的定義。** `docs/CONTRACT.md` 說三種狀態對應企畫書的「已填、
可推定但未確認、缺漏」，但鐵律 4 明訂「不得為了讓回答看起來完整而推定、補值」。
兩者字面衝突：若不得推定，什麼東西可以進 `assumed`？可能的讀法是「有預設值
但使用者未確認」，但目前沒有任何欄位定義過這種預設值。**建議：D5 一律回空
陣列，並在契約補一句說明**，否則這個欄位會變成推定的後門。

**B. 情境 2 的 `confirm_with` 不一致。** `app/rules/CLAUDE.md` 的情境表寫「—」
（無確認對象），schema 的 `household.x-refusal.confirm_with` 寫「建築師」。
但四欄位規定缺一不可，「—」會產出殘缺的一列。**建議採 schema 的「建築師」，
並修正情境表**——這是文件不一致，不是設計選擇。

**C. 情境 3 的 `blocks` 內容。** 其餘四組的 `x-refusal` 都給明確的欄位清單，
`region` 給的是 `all_regulation` 這個代號。「全部法規判定」實際包含哪些輸出
欄位、是否等於其他四組 `blocks` 的聯集，未定義。

**D. 情境 4 的比較基準與文案。** 過期門檻是 365 天，但「距今」的今是產生摘要
的日期還是別的基準日，未定義；過期警示的實際文案也沒有任何來源規定。文案
會直接顯示給使用者與評審，不應由實作者臨時決定。

**E. 值域外的值如何處理。** 追問階段只驗型別，不驗列舉值（見 #30 與 #22）。
因此可能存在「型別正確但不在允許值域內」的值。這種值算 `filled` 還是
`missing`？是否觸發對應拒答？契約未涵蓋。**這一項與 #22 留下的兩個未決邊界
（`field` 不符、列舉值非法）是同一件事，建議一起裁示。**

## 八、明確排除

本功能**不做**以下事情：

- **不做建議。** 拒答只說明無法判定什麼、要找誰確認，不給替代方案、不給
  「不過您可以考慮…」
- **不做推定補值。** 任何「查無 A 就用 B」的邏輯都不屬於本功能，跨地區推定
  尤其禁止
- **不做重新追問。** 缺漏在摘要階段揭露，不回到追問流程補問。追問只走一輪
  六組，見 `docs/specs/translation-tree.md`〈二〉
- **不做嚴重度分級。** 六個情境沒有「比較嚴重」與「比較不嚴重」之分，不標示
  優先級、不建議先補哪一項。**但輸出順序不是任意的**，見〈三之四〉
- **不做部分產出的品質判斷。** 只判斷欄位有沒有填，不判斷填得夠不夠好
- **不生成法規內容。** 所有法規、成本、氣候陳述都來自知識庫切片，本功能只
  決定「不生成什麼」
